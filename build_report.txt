7. DEFECTS FOUND AND FIXED
--------------------------------------------------------------------------------
  [1] BUILD BLOCKER - upstream main does not build
      Commit 768e8a1 added eight offset tables and the matching switch arms
      but never added the #include lines to kdlsym.c. A fresh clone fails
      with 20 undeclared-identifier errors, exit code 2.
      FIXED: all eleven tables included from kdlsym.c.

  [2] MISSING HEADER DEPENDENCY TRACKING - stale builds
      The Makefile listed only .c files as prerequisites, so make had no
      dependency on anything under include/. Touching an offset table
      produced "Nothing to be done for 'all'" and deployed stale code.
      FIXED: per-object compilation with -MMD -MP, plus -include of the
      generated .d files. Verified: touching include/offsets/12_00.h now
      rebuilds kdlsym.o and relinks; touching include/paging.h rebuilds
      main.o and paging.o.

  [3] MIXED LINKAGE CONVENTION
      13_00.h, 13_20.h and 13_60.h declared their tables as plain
      "uint64_t g_sym_map_XXXX[]" (external linkage, writable, .data)
      while the eight newer headers used "static const uint64_t". This
      breaks the moment a second translation unit needs the tables.
      FIXED: all eleven normalised to "static const uint64_t".

  [4] NO OUT-OF-BOUNDS GUARD ON SHORT TABLES
      kdlsym()/kgadget() bound-check the index against KERNEL_SYM_MAX /
      KERNEL_GADGET_MAX, not against the selected table's actual length,
      so a short table was read out of bounds.
      FIXED: _Static_assert on every table length. Verified: removing one
      entry from 12_00.h now fails the build with a static assertion.

  [5] NO CHECK ON TABLE ENTRY ORDER
      The tables are positional arrays whose order exists only in the
      trailing comments, so the compiler cannot validate it. An out of
      order table compiles, passes every bounds check, and then reads the
      wrong kernel offsets at runtime.
      FIXED: tools/check_offsets.py validates the order, the table
      lengths, the zero offsets, and that every table is both included
      and dispatched by kdlsym.c.
      VERIFIED: run against the pristine upstream clone the tool reports
      exactly the eight missing includes and exits 1; against the fixed
      tree it exits 0.

  [6] LINK FLAG IN COMPILE FLAGS
      -lSceSystemService was in CFLAGS, which is invalid for the separate
      compile step.
      FIXED: split into CFLAGS and LDFLAGS.

  [7] STALE DOCUMENTATION
      The README listed only 13.60 / 13.20 / 13.00 as supported despite
      eight further firmwares having been added.
      FIXED: README now carries the actual eleven-firmware matrix, marks
      which firmwares are tested versus merely present, and documents the
      build and the new checks.

  [8] BUILD ARTIFACTS NOT IGNORED
      .gitignore covered *.elf / *.o / *~ but not break_hv_payload/break_hv.bin
      or the generated .d files.
      FIXED: added break_hv_payload/break_hv.bin and *.d.

  [9] NO CONTINUOUS INTEGRATION
      The build break in defect [1] reached main undetected.
      FIXED: .github/workflows/build.yml builds the ps5-payload-dev SDK,
      runs the offset validation, builds the payload, and verifies the
      artifact.

8. OPEN ITEMS AND RISKS
--------------------------------------------------------------------------------
  [a] HARDWARE VALIDATION NOT PERFORMED
      Every firmware in the table above is verified to build, to dispatch
      correctly, and to have coherent offset data, but only 13.20 and
      13.60 are marked "tested" because only those have been run on a
      console. The remaining nine need hardware validation before being
      relied on.

  [b] DUPLICATE OFFSET TABLES - PROVENANCE UNVERIFIED
      12.40 is byte-identical to 12.20 and 12.70 is byte-identical to
      12.60. This is plausible, since a firmware update that ships no
      kernel rebuild leaves every symbol where it was, but it has not been
      confirmed against independent kernel dumps for 12.40 and 12.70. If
      either pair is wrong, the exploit will operate on wrong addresses.
      Action: verify against a kernel dump for 12.40 and 12.70.

  [c] HARDCODED STRUCT OFFSETS IN include/paging.h
      KERNEL_OFFSET_VMSPACE_VM_PMAP is hardcoded to 0x1D8 and
      KERNEL_OFFSET_PROC_P_VMSPACE to 0x200. The SDK tracks the
      equivalent offsets per firmware (0x2E8 and 0x1D0 for 12.xx and
      13.xx) and exposes them as runtime variables. The project's 0x1D8
      refers to a different field, so it is not directly comparable, but
      it is version sensitive by the author's own comment and is not
      derived from the SDK.
      Impact: LOW at present. get_proc_pmap() is the only consumer and it
      is not called anywhere in the exploit path, so the value is
      currently dead. It becomes a live bug the moment that function is
      wired up. Action: replace with the SDK's firmware-aware values, or
      derive the offset per firmware, before using it.

  [d] KERNEL_OFFSET_PMAP_PM_PML4 (0x020) is likewise hardcoded and
      firmware sensitive, and is used by find_pml4e().

  [e] make debug requires gdb-multiarch, which is not installed in this
      environment. The debug target cannot be exercised here.

  [f] The upstream repository at github.com/EchoStretch/Byepervisor-Reborn
      is still unbuildable for anyone cloning it. The fix in this tree is
      committed locally and has not been pushed.

10. SUMMARY
--------------------------------------------------------------------------------
  The project now builds cleanly and dispatches correctly for all eleven
  requested firmwares (12.00 through 13.60). Three defects that would
  each have caused a wrong or stale payload in the field were found and
  fixed: the missing includes that made upstream unbuildable, the missing
  header dependency tracking that silently shipped stale offset tables,
  and the missing bounds and ordering validation that would have let a
  malformed offset table reach the console.

  Remaining work is hardware validation of the nine untested firmwares
  and confirmation of the 12.40 / 12.70 offset provenance.

  WHAT THIS ESTABLISHES
    - The 12.20 offset table is correct: all 14 kernel symbol offsets and all
      21 gadget offsets resolve to the right addresses on a real console.
    - The gadget set required by the exploit chain is present on 12.20.
    - The SDK resolves the 12.xx kernel text base correctly. The SDK maps the
      whole 12.00 - 12.70 range to KERNEL_ADDRESS_TEXT_BASE =
      KERNEL_ADDRESS_DATA_BASE - 0x0D50000, and the 12.20 result confirms
      that value is right.
    - The exploit chain and the rest-mode resume path work end to end.
    - The 12.20 support added by upstream commit 768e8a1 is functional, not
      just present.

  WHAT IT DOES NOT ESTABLISH
    - Nothing about the other ten firmwares. They remain untested.
    - 12.40 is byte-identical to the verified 12.20 table, so it should work
      on the same kernel, but it has not been run and its table was copied
      rather than independently derived.
    - 12.60 and 12.70 are byte-identical to each other and differ from the
      verified 12.20 table in exactly one symbol, KERNEL_SYM_HV_MP_STARTUP_CALL
      (0xC9DF50 in 12.20, 0xC9DFB0 in 12.60/12.70, a delta of 0x60). They are
      therefore only as good as that single unverified symbol.
    - 12.00 and 12.02 use a different table from the rest of the 12.xx range
      and are not covered by the 12.20 result.

  Consequence for section 8(b): the 12.40 / 12.70 provenance question is
  narrowed but not closed. 12.40 is a copy of a table now known to be correct;
  12.70 depends on one symbol that differs from it.
